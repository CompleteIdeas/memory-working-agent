Findings

critical F01 — The browser's address guard is not applied to redirect hops, so a public page can send the agent browser to a private address · open

ctx.route('**/*') in src/tools/browser.ts checks urlRefusal(u) on each request, and browser_open checks the first URL. Neither re-checks where an HTTP 3xx redirect lands. Measured against this review's own local instance: browser_open on a public https://httpbin.org/redirect-to?url=... that pointed at 127.0.0.1:7863 returned MWA's own /api/health, /api/conversations and /api/logs to the agent as page text, and a redirect to /api/chat?message=... started an agent run (it answered 'ok', $0.0238). The code comment already flags the DNS-rebinding variant ('a name rebound between the check and the request is not caught'); redirects are a second, simpler path to the same place. browser_open http://127.0.0.1 directly is refused cleanly, which is what makes the redirect gap easy to miss.

Fix: In the route handler, refuse on redirect responses too (check response status/location, or abort any request whose resolved address is private regardless of how it was reached); re-run urlRefusal on the post-redirect URL.

high F04 — 'go ahead' re-opens the page and wipes the form before submitting · open

The GO_AHEAD click must be in the same message as the request (src/tools/browser.ts). So the natural two-turn flow (fill, then 'ok submit it') starts a fresh turn in which the agent re-opens the page to re-establish the control numbers, which clears what it just typed, then submits an empty form. Seen in S3 (submitted empty) and S4 (reported the saved login as invalid when it was correct, because the password field had been re-emptied). The design intends the opposite: fill, confirm, submit.

Fix: Keep the page state across the confirm turn (don't force a re-open), or re-fill from the prior turn's values/vault refs before the confirmed click.

medium F10 — browser_open output is squeezed twice: a 9,000-char cap in the tool, then a ~2,500-char relevance trim, and the person is never told · open

browser.ts caps page text at MWA_BROWSER_MAX_CHARS (9,000) and the controls list at 150. agent.ts then runs the same relevance trim used for fetched pages (src/trim.ts, ~2,500 chars) over the whole browser_open result. Measured on npr.org/sections/news: 20,717 chars -> 2,937, with 9 of 54 body lines kept and 0 of the lead story's paragraphs; on the useventing calendar both hard caps bit (150 controls, text cut at 9,000) before the trim took it to 2,931. The trim is tuned for prose, so on a control-heavy page it keeps numbered links and discards the article text the question was about. The agent is not told the snapshot was cut, so it reports the gap as the page's fault ('it cuts off the leading headlines').

Fix: Don't relevance-trim browser_open the way fetched prose is trimmed (it already has its own cap), or trim the body separately from the controls list; surface 'snapshot trimmed' to the model so it navigates instead of giving up.

Browser in the back end

Robert's ask: "make this a function where it can run browser stuff kind of in the back end." Here is what that does and does not do today.

What works unattended today

  • Read-only browsing: open pages, click non-consequential links/buttons, read, screenshot. Bounded by MWA_PAGE_BUDGET (default 15 pages) and the 30 s nav timeout. Proven: S5a wrote a two-site headline briefing from a background job ($0.013); S5b's daily title-change watch ran, saw no change and stayed quiet.
  • A sign-in that needs no consequential click AND whose session is already live in that person's browser profile: S5c run 1 reported the secure area — but only because an earlier attended chat had signed in; it did not sign in itself.
  • Honest reporting back: the clock-prefixed chat turn and Work view show steps, tool calls and cost, and the refusals are surfaced to the person (if not explained).

What is refused, and why (from the code)

A consequential click (submit/pay/buy/send/...) in an unattended run
browser_click: if (ctx.interactive === false) throw new ToolRefusal(`(refused: "${label}" would send, pay, delete or submit something, and nobody is watching this run. Say in your summary what is ready to be clicked.)`)

A run nobody is watching must never take a consequential action. Correct and important.

Typing a saved vault value in an unattended run that has read outside content
browser_type: if (ctx.interactive === false && ctx.tainted) throw new ToolRefusal('(refused: a saved login is not typed by an unattended run that has read outside content)')

Stops a page/email from steering a background run into spending a saved secret. But a sign-in job reads the login page first, which taints it, so this also blocks the ordinary, intended case — see the gap below.

Connecting an account or saving/forgetting a vault entry from an unattended or tainted run
connect.ts vault_request/connect_account/vault_forget: if (ctx.interactive === false) ... if (ctx.tainted) ...

Secrets are only ever captured with the person present. Correct.

The gap

The two refusals above mean an unattended sign-in is impossible almost by construction: browser_open on the login page taints the run, so browser_type refuses the vault value, and clicking Login is a consequential click, which refuses too. MWA nonetheless accepts 'every day, sign in...' at scheduling time with an encouraging message and only fails at run time with wording that states the block but not the reason (F06). So 'browser stuff in the back end' works for reading and summarising, and does not work for anything that signs in, submits or buys.

What a safe design for unattended browsing would need

  • Site-scoped vault use without the blanket taint block: allow an unattended run to type a vault value when the open page's host matches the vault entry's own site (the scoping resolveVaultRefs already enforces), even though reading that site tainted the run. The taint rule should gate sending a secret to OTHER sites, not to the entry's own site.
  • Consequential-click handling for unattended runs: a pre-authorised, narrowly-scoped allowance set when the job is CREATED by the present person (this job may click Login on the-internet.herokuapp.com), checked against the actual control and host at run time — rather than today's all-or-nothing refusal. This is the local equivalent of Muse's Sentinel approving a specific destination/purpose.
  • An outward-action budget that counts the right things: today browser_open is exempt and only clicks/typing count toward MAX_EXTERNAL (3). A sign-in-and-report job should get a small, explicit budget of consequential actions scoped to the authorised site, and pause-and-notify (not silently fail) when it would exceed it.
  • Honesty at scheduling time: detect that a job needs a sign-in or a consequential click unattended and either arrange the pre-authorisation above or tell the person up front that it will pause for them, instead of promising success and failing daily.
  • Fix the redirect gap (F01) first: an unattended run that CAN sign in and click is exactly the one that must not be reachable from a redirected page into a private address.

Function inventory

Can do

  • Open a page and read it as text with up to 150 numbered controls (browser_open). Playwright drives headless Chromium, 1280x900, one persistent profile per person (data/browser/<person>), so sites stay signed in across runs and restarts.
  • Click a control by number (browser_click) and type into a field by number (browser_type).
  • Type a saved secret with {{vault:entry.field}} — filled in only when the open page is on the entry's own site or a subdomain; the model never sees the value, and saved values are masked out of tool output.
  • Save a screenshot of the visible page to the person's Files (browser_screenshot).
  • Treat page text as untrusted: fenced as EXTERNAL CONTENT, taints the run, injection held in testing (S9).
  • Fall back to read_document for a URL browser_open cannot render (PDF in S7).
  • Run read-only browsing in a background 'work on it' job or a scheduled job, and report back in the chat / Work view with step count, tool count and cost.

Cannot do

  • Choose an option in a <select> dropdown (no select tool) — F05.
  • Scroll or paginate; lazy-loaded / long pages are unreachable — F14.
  • See content inside iframes, including consent/cookie walls — F13.
  • Click a consequential control (send/submit/pay/buy/delete) unless the person's message THIS turn says go ahead; never in an unattended run.
  • Type a saved secret in an unattended run that has read outside content (tainted).
  • Keep a filled form across a confirm turn — the confirm re-opens the page and wipes it (F04).
  • Reach a loopback/private address directly (refused) — but a redirect bypasses the guard (F01).
  • Be stopped or steered from the web UI (API only) — F15.
  • Use a one-time payment card, an isolated per-task VM, or a second approver agent (none exist).

Caps

  • Page text: MWA_BROWSER_MAX_CHARS, default 9,000, then a further ~2,500-char relevance trim in agent.ts (F10).
  • Controls per snapshot: 150 (hard-coded).
  • Navigation timeout: MWA_BROWSER_TIMEOUT_MS, default 30,000 ms.
  • Background page budget: MWA_PAGE_BUDGET, default 15 pages per unattended run.
  • Unattended outward-action limit: MAX_EXTERNAL = 3, but browser_open is NOT counted as outward reach (clicks and typing are) — so reading pages is effectively bounded by the page budget, not the tripwire.
  • Concurrency: MWA_MAX_CONCURRENT default 4 runs, but all of a person's runs share ONE browser page (F02).

Rules

  • Consequential click: words matched by CONSEQUENTIAL (send|submit|pay|purchase|buy|order|checkout|delete|confirm|transfer|withdraw|refund|publish|post|approve|unsubscribe...). Held unless the person's own message this turn matches GO_AHEAD (yes|go ahead|do it|submit it|send it|confirm|approve|proceed|click it). Unattended: always refused.
  • Vault scoping: a value is sent only to its entry's own host or a subdomain; a vault ref in a URL is refused; unattended+tainted run cannot type a vault value.
  • Address guard: every request checked with urlRefusal (loopback/private refused); not re-applied on redirect (F01); DNS rebinding acknowledged as uncaught in-code.
  • Page text is outside content: fenced, taints the run, never instructions.

What the UI shows

  • Live run: one line 'Working...' with the last step label and a 'details' toggle; no live page preview; no Stop/steer (F15).
  • After a run: a 'what I did - N steps' spine (raw tool names + 'Using a tool' filler, F16) and a 'What I did: Reached outside your machine' reach summary.
  • Vault/connect: a setup card above the chat box (BL-62/63), clear copy, 5-second poll to appear. No standing vault manager page; vault_list is a tool, not a screen.
  • Screenshots land in Files; open in a viewer with Download/Share/Pop out, correct at 1440 and 390; not shown inline in chat.
  • Scheduled/background browser results arrive as a chat turn prefixed with the clock glyph and a 'ran unattended - steps - tool calls - $cost' line, plus the Work view.
